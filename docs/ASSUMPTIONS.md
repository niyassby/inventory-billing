# Assumptions and Defaults

The Master Prompt says to make reasonable assumptions instead of asking, choose the safest sensible default, and record each one here. Every entry can be revisited. Changing one only means updating the referenced setting or decision.

| # | Area | Assumption / decision | Why | Revisit if… |
|---|---|---|---|---|
| A-1 | Process | The project had no git repository. Phase 0 ran `git init` (branch `main`) and committed the untouched code as `d38c517` before writing anything else. | §15 asks for a commit after every step. §16 asks for a backup before any change. | You already keep this code in another repo. In that case, import the history there. |
| A-2 | Process | Commits use the configured email `applenetdesign@gmail.com`. `user.name` was not set in git, so commits pass the Windows username (`niyas`) inline. Global git config was not changed. | Commits need an author name. | You want a different author name. Set `git config user.name`. |
| A-3 | Architecture | The Master Prompt names "Option A" and "evaluate both options" but never describes Option B. I defined Option B as multi-master local-first sync and evaluated A against it. **Option A (LAN hub) chosen** (ARCHITECTURE D-1). | Correct stock and legal numbering come first. A single writer is the simplest reliable design. | You run several branches that must trade while disconnected from each other. |
| A-4 | Architecture | One app binary with **standalone / hub / client** modes. Standalone stays the default, so a single-PC shop sees no network complexity. | It keeps today's behaviour and only adds the LAN where it is needed. | — |
| A-5 | Architecture | Tablets and phones use the hub-served web UI, online only (no browser outbox) in v1. | A browser outbox (IndexedDB) roughly doubles the sync-test surface. | Mobile counters must sell during hub outages. |
| A-6 | Offline policy | Default `network.offline_sales_policy = allow_reserved_numbers`. Clients lease invoice-number blocks per device sub-series, and offline oversells are recorded and flagged, not rejected. | A shop must not stop billing because the back-office PC rebooted. Per-device series keep numbers unique and sequential. | Your tax authority requires a single series for all counters. Then use `block`. |
| A-7 | Validation | "One shared Zod schema package used by both frontend and backend" is not possible literally, because the backend is Rust. Instead, **Rust DTOs are the source of truth**: TS types are generated with `specta`/`tauri-specta`, and Zod schemas in `packages/shared` cover forms and are tested for parity against the generated types. The backend re-validates everything. | Backend validation is mandatory for security, and code generation prevents drift. | — |
| A-8 | Stack | Keep **Vite** (not Next.js), because the app is already Vite and a Tauri desktop app has no use for SSR. Keep shadcn on base-ui, Tailwind 4, TanStack Query, and Zustand for UI state only. Standardize on **one icon set (Lucide)** and drop Hugeicons to shrink the bundle. | Matches the existing app (§6 "whichever matches"). | You prefer the Hugeicons style. Then keep it and tree-shake it properly instead. |
| A-9 | Stack | The frontend moves to `packages/shared` + `src/` in a single repo using npm workspaces (not a larger monorepo tool). | It is the simplest setup that satisfies "`packages/shared` module". | The repo grows to several apps. |
| A-10 | Platform | Windows 10/11 x64 is the primary target and the hub OS. macOS and Linux builds are kept compiling but are second-tier. | The current development machine and typical SMB counters are Windows. | — |
| A-11 | Locale | Default business profile: **India**, currency **INR (paise)**, tax **GST** (CGST+SGST / IGST, inclusive or exclusive per price list), financial year starting **1 April**, timezone **Asia/Kolkata**. All of it is configurable. VAT and "no tax" profiles ship as well. | The ₹ symbol exists in the current preferences, and GST appears in seed data ("GST 18%"). | You operate in another country. Onboarding asks anyway. |
| A-12 | Money | Money is `i64` in minor units, with 2 decimals by default (3 for currencies like KWD via currency metadata). Quantities are `i64` scaled by 1000 (3 decimals), which is enough for kg, litres and metres. Rounding is half-up on each line's tax. Invoice-level rounding to the nearest ₹1 is optional (a setting) and posts a round-off line. | It is the common Indian GST practice and deterministic. | Your accountant prefers tax computed on the invoice total. That is a setting. |
| A-13 | IDs | New rows get UUIDv7 primary keys. **Existing UUIDv4 IDs are kept as they are** during migration. Both are stored as `TEXT`. | Rewriting IDs would break references and the audit trail. | — |
| A-14 | Scope | **Leads (CRM pipeline)** and the **chart of accounts / manual journals** exist today but aren't in Master Prompt §4. They are kept and migrated, but get no new features until the core modules are done. | Removing user data or features is not allowed without a migration path (§16). | You want them removed. |
| A-15 | Scope | Licensing, cloud sync, e-invoicing (IRN/QR from the government portal), payment-gateway integrations and multi-branch replication are **out of scope**. They are listed as suggestions only. | §9 and §16. | — |
| A-16 | Roles | Legacy roles map as `admin → Owner`, `manager → Manager`, `accountant → Accountant`, `staff → Cashier`. A new **Stock Keeper** role is added, and custom roles are allowed. | It preserves current access while adding the roles from §9. | — |
| A-17 | Security | The seeded `admin@example.com / password123` account is **not migrated as-is**. If its password still matches the default, the account is flagged and the owner must set a new password on first login. Fresh installs create the owner in onboarding (no default password). | S-1 in the audit. | — |
| A-18 | Encryption | Encrypted backups (AES-256-GCM) are in v1. **SQLCipher at rest is optional** and off by default until it is benchmarked on low-end hardware (the §12 targets) and its key recovery is documented. | A lost DB key destroys the business data. Prefer safe recovery. | Your threat model includes theft of the shop PC. Then enable it. |
| A-19 | Migration | The legacy invoices have no snapshot. Snapshots are **back-filled from the current product, tax and customer data** at migration time and marked `snapshot_source = 'migrated'`. They are a best effort, not proof of the original sale. | No other source of historical data exists. | — |
| A-20 | Migration | Settings currently in `localStorage` (company name, phone, address, tax no, receipt header and footer) are imported once into the DB on the first launch of the new version. The currency symbol was never persisted, so it is asked in onboarding. | Prevents losing what the user typed. | — |
| A-21 | Dates | Business dates use the configured business timezone, not UTC. Timestamps are stored as UTC RFC 3339 next to a local `business_date` column. | B-20 in the audit. | — |
| A-22 | Hardware | Thermal printing uses ESC/POS over USB, serial or network (raw TCP 9100) from the hub or the local client, with 58 mm and 80 mm templates. A browser-print fallback is kept. Barcode scanners are assumed to be keyboard-wedge devices. | These are the most common SMB devices. | You use OPOS or JavaPOS drivers. |
| A-23 | Process | The phases are done strictly in order, and each phase stops for your review (§15). Phase 0 changed **no source code**, only `docs/` and the git baseline. | Explicit in the Master Prompt. | — |
| A-24 | TS migration | Legacy pages stay `.jsx` (with `allowJs`, not type-checked) until their module is rebuilt in Phases 5–7. The status table is in DEVELOPER.md. | It keeps the app working after every step (§6) without wasted effort. | — |
