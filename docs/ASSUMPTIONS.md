The Master Prompt says to make reasonable assumptions instead of asking, choose the safest sensible default, and record each one here. Every entry can be revisited. Changing one only means updating the referenced setting or decision.

| A-30 | Migration | After migration, each customer's and supplier's balance **equals what v1 showed**, even where v1's figure was produced by a bug (B-4 overpayments) or a manual edit (B-14). Silently changing what customers owe would be worse than flagging it. | The owner wants v1 balances recomputed from documents instead. That is a one-line change in `reconcile_party_balances`. |
| A-31 | Migration | v1 stock is carried over as **one opening movement per product, dated the migration day**. v1's adjustment history is archived (`legacy_records`) but not replayed. | v1's adjustment log double-counts sales (B-11) and can't rebuild the stock figure. The current figure is the only reliable one. | — |
| A-32 | Migration | v1 invoice lines have no per-line tax split. The invoice's tax is spread over the lines in proportion and stored as `other_tax` (not CGST/SGST). `unit_cost` on migrated lines is the product's cost at migration time. Both are marked by `snapshot_source = 'migrated'`. | v1 never stored these values. | — |
| A-33 | Migration | v1 payments marked `CREDIT` (audit B-5) or with an unknown method are migrated with mode `other` and reported, not reclassified as unpaid. | The money may really have been received. Only the owner knows. | — |

| A-35 | Schema | Every product has at least one **variant** (the SKU). Simple products have exactly one. Stock, prices, barcodes and document lines reference the variant. | It is one model for simple and variant products, with no special cases in stock or billing. | — |
| A-36 | Schema | Quotations, sales orders and delivery challans share one table (`sales_documents`). Credit notes are `sales_returns` (restock optional per line). | These documents share their shape and never touch the ledgers. | — |
| A-37 | Cutover | From Phase 3 the app opens **both** databases. `inventory_v2.db` is created (empty, migrated) at startup and serves the v2 commands. The screens keep using v1 until each module is rebuilt in Phase 5, when the v1 data is migrated and the app switches over. `migrate-legacy` may replace the v2 file only while it is provably unused (no users, branches, products or invoices). Anything else is refused. | The app keeps working after every step, and no v1 data is touched before the owner sees the migration report. | — |
| A-38 | Contract | The TS types come from **`schemars` + `json-schema-to-typescript`**, not `specta`. The Rust command list writes `packages/shared/src/generated/api-schema.json` (a test fails when it is stale) and `npm run gen:api` turns it into `api.ts` (CI fails when that is stale). | `specta` would need release-candidate crates for Tauri 2. A JSON schema is a stable, inspectable contract that the Phase 4 HTTP API can reuse as is. | `tauri-specta` 2 is stable and the schema step becomes a burden. |
| A-39 | API | Every v2 command takes the same arguments, `{ token, input, approval? }`, and returns `{ code, message, details }` on failure. Public commands (setup, sign-in) ignore the token. | One envelope for IPC and, in Phase 4, HTTP. Screens never deal with transport details. | — |
| A-40 | Approvals | Manager approval is **inline and per request**: the service returns `APPROVAL_REQUIRED` with the permission and reason, the UI asks a manager for their PIN or password, and the same request is retried with `approval`. The approver needs the permission itself **and** `approvals.grant`. It is recorded in the audit log as `approved_by`. Needed for: discounts and price overrides above the cashier's rights, selling over a credit limit (`sales.credit_override`, new), backdating, voids, returns, selling-price changes and voiding purchase bills. | It matches how a shop works: the manager walks over and types a PIN. Nothing is stored as "pending". | You want remote approval requests. That is a Phase 4 notification. |
| A-41 | Inventory | Valuation is **weighted average cost**, updated on every receipt. FIFO (setting `inventory.valuation_method`) is accepted but not implemented yet and behaves as weighted average. Goods receipts debit Inventory and credit **Goods Received Not Invoiced** (account 2050, new). The bill clears GRNI. Price differences go to Stock Adjustments and rounding to Round-off. | Weighted average is the common SMB method, and GRNI keeps the books right when goods and bills arrive on different days. | Your accountant needs FIFO (planned for Phase 6 reports). |
| A-42 | Inventory | Default `inventory.negative_stock_policy = block`. A sale that would take stock below zero fails with `INSUFFICIENT_STOCK`. `warn` allows it and returns a warning, and `allow` stays silent. Stock transfers between stores are immediate (no "in transit" state). | Overselling causes silent accounting errors. Blocking is the safest default. | You sell before receiving goods. Then switch to `warn`. |
| A-43 | Tax | Default `tax.round_total_to = 100` (round the bill total to ₹1, posted to Round-off), `tax.prices_include_tax = true`. A return carries the invoice's round-off back pro rata, and the last return takes the remainder so the totals close at zero. A refund may not exceed what the customer actually paid. | Common Indian retail practice. It stops a return from paying out cash that was never received. | — |
| A-44 | Security | Sessions last 12 h with a 30-minute idle timeout. Accounts lock for 15 minutes after 5 failed sign-ins (and sign-in is rate limited per email). The minimum password length is 10. Tokens are random, stored only as SHA-256 hashes. PIN sign-in is optional (`security.pin_login_enabled`). The last active owner can't be deleted, demoted or disabled. | Safe defaults for a shared counter PC. All are settings. | — |
| A-45 | Network | The LAN API is **HTTPS on port 47900** with a self-signed certificate made on first start (ECDSA P-256, `rcgen`; TLS by `rustls` with the `ring` backend, so the build needs no cmake/nasm). The certificate file sits next to the database, its private key in the OS keychain. Counters pin the certificate's SHA-256 at pairing. Pairing is: the counter shows the fingerprint it sees, the person compares it with the code on the hub's screen, then types a 6-digit one-time code (5 minutes, rate limited to 10 tries per 5 minutes). Only private, loopback and link-local addresses (plus `network.allowedSubnets`) may connect. | A shop LAN has no certificate authority. Pinning plus a visual check stops a machine pretending to be the hub, without any setup. | You want a certificate from your own CA. |
| A-46 | Network | Secrets (a counter's device credential, the hub's TLS key, the backup key) live in the **OS keychain** (Windows Credential Manager via `keyring`). Device credentials and session tokens are stored on the hub only as SHA-256 hashes. A session started over the LAN works only on that device; LAN sessions are refused in the hub's own window. | Nothing secret in the database or plain files. | — |
| A-47 | Scope | Tablets and phones (hub-served web UI, D-3) are **not in Phase 4**. The HTTP API is ready for them, but serving the UI, a browser pairing flow and a browser transport come with the Phase 5 screens. | The current screens still use v1. A browser client needs its own sign-in and pairing UI. | — |
| A-48 | Offline | Offline, a counter only makes **fully paid sales at catalogue prices**, with discounts within the cashier's own limit. Credit sales, price changes, manager approvals, back-dating, conversions and every non-sales action need the hub (HUB_OFFLINE). Only users already signed in on that counter can work offline; their session is checked by the hub at sync (it must belong to that device and have been valid at the time of the sale). | The hub can't check credit limits or a manager's PIN while it is unreachable. A paid sale is safe to accept and reconcile later. | You need offline credit sales. That would be a policy with a per-customer offline limit. |
| A-49 | Offline | Offline numbers come from a per-device series (prefix = the device's short code, for example `C2/26-27/00001`) in leased blocks of `network.leaseSize` (50), topped up when half are used. Leases are for the current financial year: across 1 April a counter needs one online moment. Numbers of a lease that was never used stay unused (a gap that the lease table explains). | Each series stays sequential on its own (A-6). | — |
| A-50 | Offline | The counter's queued sale carries the prices the customer paid and the total it printed. The hub posts it at those prices (not the current catalogue's) and refuses it with TOTALS_MISMATCH only if its own pricing of those prices differs (for example a tax rate changed meanwhile). Price differences, oversells and clocks off by more than `network.maxClockSkewHours` (24) are recorded in `sync_exceptions` for review, never auto-corrected. The hub's clock dates the sale (counter time corrected by the measured skew). | The receipt the customer holds is the record. | — |
| A-51 | Offline | If a sale was sent online and the answer was lost, then queued offline, the hub refuses the offline copy (same request id, different request: CONFLICT). It appears as a refused sale for a manager to discard. It is never billed twice. | Billing twice is worse than one extra review. | — |
| A-52 | Offline | The catalogue a counter caches is a full snapshot every 15 minutes (and when the hub comes back), not an incremental feed. Customers are cached by name, phone and GSTIN only. | Simple and fast enough for a few thousand items. Incremental sync is a Phase 7 performance item. | Your catalogue has more than about 20,000 items. |
| A-53 | Backup | Backups are a SQLite online-backup copy, integrity-checked, **zstd**-compressed and, **once the owner sets a backup passphrase**, encrypted with AES-256-GCM (key from Argon2id; header authenticated). Until a passphrase is set, backups are compressed but not encrypted, and the backup status says so. Default schedule: daily at 21:00 plus every 4 hours while the app runs; retention 7 daily, 4 weekly, 12 monthly; manual backups are never pruned; the 5 newest safety (pre-restore) copies are kept. | Forcing a passphrase at setup would block the first sale. A lost passphrase makes encrypted backups useless, so it is a deliberate owner step. | — |
| A-54 | Backup | Restore is **live** (SQLite backup API into the open database) after the file is fully verified and a safety backup is taken. Older backups are migrated forward; backups from newer app versions are refused. Everyone is signed out. Restore, setting the passphrase and checking a file only work on the hub or standalone PC itself. | No restart, and no window where the database file is half replaced. | — |
| A-55 | Jobs | Background jobs (backup, hourly low-stock notices, weekly integrity check, daily cleanup of expired sessions, request ids older than 30 days and used pairing codes) run on the hub and standalone PCs, never on counters. Report caching is left to Phase 6 with the reports. | The hub owns the data. | — |
| A-56 | Permissions | New permissions: `devices.manage` (pair and remove counters) and `sync.review` (offline exceptions, discarding refused offline sales), for owners and managers. Changing the backup settings also needs `backup.manage` (owner only). | Same split as user and backup management today. | — |
| A-57 | Mode change | Changing this PC's role (standalone, hub, counter) needs an owner's or manager's sign-in (`settings.manage`) once the PC holds a business, takes effect after a restart, and is refused on a counter with unsent or refused offline sales. Switching a PC that has its own data to counter mode doesn't delete that data; the local database just stays unused. | No silent data loss, no half-switched state. | — |
| A-58 | Cutover | Phase 5 switches the screens to v2. On the first start of the new version: if the old database (`inventory_app.db`) is present, the owner is offered **"Check my data"** (a dry run with the reconciliation report) and then **"Import my data"**; otherwise a short setup creates the business. The import builds v2 in a temporary file and copies it into the (unused) v2 database; the v1 file is never written and a backup copy is kept. Until Phase 6, **reports, accounts, settings, leads and barcode-label printing** show "coming in the next update"; their data was imported and nothing is lost. The old v1 pages for them stay in `src/pages` as reference until they are rebuilt. | The core modules (sales, stock, purchases, parties) had to move together: v1 and v2 can't both write. | You need one of those screens before Phase 6. | A-59 | Dev | A development-only HTTP bridge (`src-tauri/src/bin/dev_server.rs`, `npm run dev:bridge`) serves the v2 commands on 127.0.0.1:1430 so the screens run in a normal browser and in Playwright. | A-60 | Printing | Receipts (58 and 80 mm) and A4 invoices, quotations and orders are HTML printed through the system print dialog; "Save as PDF" in that dialog makes the PDF. | A-62 | Setup | A new business gets default units (pcs, kg, g, ltr, ml, m, box, pack, dozen) and, under GST, the standard rates 0/5/12/18/28 %. All can be edited or removed. | The first product can be added straight after setup. | — |
